# Spool 识别与更新：研究决策记录

[English](../../spool-identity.md) · 中文译文，以英文为准。 · [中文目录](../README.md)

状态：研究与提议方向，2026-10-24。本文件未实现任何新的 manifest 字段、发布者验证、升级操作或签名支持。

当前宿主提供了一个有界的只读 `spool-release-diff` 和真正的独立新实例延续。Loom 的 v1/v2 CLI 配对包验证两个实际版本并检查此交接。这是按字节/请求进行的审查，而不是下面所提议的授权血统或原地迁移。现有格式保持不变；请参见 [native handoff](../../native-spool.md#release-review-and-independent-continuation)。

## 当前实现所建立的内容

`src/manifest.rs` 将包名、版本、描述和一个排序后的文件清单绑定到一个发布摘要。`src/release.rs` 也检查归档、程序、源代码和声明的哈希值。这可以检测本地发布合同中的内容不匹配。它不会验证发布者、保留命名空间或证明两个发布属于授权更新血统。版本验证器接受一个有界的数字形式；不要声称完全支持 SemVer。

## 四个不同的问题

| 问题 | 提议的证据 | 无法单独建立的内容 |
| --- | --- | --- |
| 这是否是完全相同的发布？ | 验证的清单和负载摘要 | 发布者身份或行为安全性 |
| 这是否是同一 spool 的授权后续版本？ | 稳定的发布者范围身份、授权发布关系和验证的权威 | 领域行为的兼容性 |
| 该实例是否可以升级？ | 运行时/输入/输出合同、状态迁移证据和权限审查 | 相同的未来模型响应 |
| 这是否是同一正在运行的实例？ | 宿主实例身份和已提交的检查点血统 | 发布字节的相等性 |

稳定的标识应能经受普通发布、仓库重命名或批准的发布者密钥轮换。复制的标识符或父哈希值只是在与受信任的发布者/注册中心权威进行比对前的声明。授权的分支会获得新的标识，并可以声明其来源；它不会静默继承原始实例的更新权限。

## 重用与限制

- [SemVer](https://semver.org/) 用于传达声明的公共接口的兼容性意图。它不能决定领域等价性，也不是更新授权。在解释一个版本提升前，请先定义 spool 的公共合同。
- [Package-URL](https://tc54.org/purl/) 提供了一个标准的包坐标词汇。研究其命名空间/名称/版本模型，而不是发明一个不兼容的定位符或未注册的生态系统类型。坐标不是经过验证的发布者凭证。
- [SLSA 构建溯源](https://slsa.dev/spec/v1.2/build-provenance) 将产物主体与构建定义、依赖项和运行细节分离。重用这种分离作为证据。现有的 Loom 哈希不声称符合 SLS, 或一个可信的构建证明。

从一个操作员拥有的本地权威记录和摘要固定的发布开始，作为首次接受。在远程更新发现之前，评估现有的签名/更新元数据系统，包括密钥轮换、撤销和回滚保护。不要引入未经审查的自研签名协议。

## 提议的责任划分

Loom 验证作者元数据，计算清单并附加识别的检查和提议的血统。由发布者控制的发布基础设施提供授权证据。宿主独立验证准入并为一个实例选择一个发布。spool 提供领域兼容性和迁移规则。后端快照既不是发布者凭证也不是状态模式。

不要将新版本或相同逻辑身份视为扩展功能的许可。应比较有效的请求、入口点、依赖项、代理指令、工具和网络需求。由大型语言模型生成的兼容性报告仅作为建议；领域测试和操作员的升级策略决定最终结果。

实例升级必须绑定旧版本/检查点和提议的新版本，并明确状态模式的前置条件。迁移将在一个全新的授权尝试中执行；失败将保留旧的已提交检查点。在成功迁移后切换回旧代码不会自动逆转状态或外部影响。下游消费者将继续固定已接受的构件版本修订，无论生产者是否升级。

## 在添加通用版本服务之前进行首次接受

1. 在一个本地授权的逻辑身份下发布两个不同的版本。
2. 拒绝来自不同发布者、未经授权的分支和使用不同摘要但相同版本标签的重用；仅通过策略文档化的授权转移才被允许。
3. 展示重命名变更不会改变逻辑身份或现有固定点。
4. 要求对功能增强进行审核，并拒绝过期的实例检查点。
5. 展示一次兼容的更新和一次失败的状态迁移，保留旧的已提交状态。不要推断任意的行为等价性。

待定决策：逻辑-ID 编码、授权存储、依赖锁定格式、多平台版本变体、密钥管理和迁移证据格式。将这些研究问题与当前包格式分开。
