# Nextflow执行、中断和文件管理

[English](../../nextflow-observation.md) · 中文译文，以英文为准。 · [中文目录](../README.md)

状态：原生macOS接受，2026-10-24。本报告区分了未修改的上游工作流、本地生成文件的固定 fixture 和单独审查的宿主配置文件。这不是对任意Nextflow管道或代码代理的资格认证。

## 重现路径

先前的Loom文档PR #2已合并，并且所有三个必需检查均已通过。Java已安装，Nextflow 26.10.3的官方分发版本已验证其发布SHA-256。上游的hello源码已验证其锁定提交和Git blob身份。确切的源码、命令和必需的宿主操作在[示例](../examples/nextflow/README.md)中。

接受运行不使用LLM。Python的标准库仅驱动固定操作器 fixture 并读取诊断库存。执行策略、进程所有权、精确批准、正式产物发布和scratch收集是Rust宿主的责任。通用Loom打包不需要Java或运行中的宿主。

1. 不修改上游hello源码，运行上游hello。一个小的标记包装器将stdout重定向到声明的交付物。
2. 运行本地的两个准备/两个完成工作流，完成其所有步骤。使用现有宿主存储接收其两个声明结果文件作为不可变修订。
3. 运行本地工作流再次；在其中一个完成结果发布后停止，同时另一个完成任务仍在运行。活跃收集被拒绝。发送SIGINT到真实宿主CLI，然后验证一个取消的、终止确认的接收。
4. 拒绝部分输出接受。保留原生的工作/缓存，并显式继续从选定的前继者使用Nextflow `-resume`。
5. 观察实际恢复跟踪中的三个缓存任务和一个完成/重新计算任务。接收两者的结果，检查出锁定修订，显式放弃恢复并收集scratch。再次检查出相同的修订并比较字节；拒绝后续恢复。

结果的正式字节是`ALPHA\n`和`BETA\n`，两者在普通和中断/恢复情况下具有相同的摘要哈希值。修订身份可能不同，因为它们也绑定生产者证据。原生任务ID、临时文件名和库存大小不同；接受断言关系，而非其偶然的随机值。见[可移植证据](../../acceptance/nextflow-local.json)。

## 观察文件和所有权

| 观察路径/类 | 该实验建立的含义 | 宿主处理 |
| --- | --- | --- |
| `.nextflow/cache/<session>/db/` 和会话索引 | 本机任务缓存，包括数据库日志/表/锁文件 | 在选择恢复时保留工作文件；不将这些视为宿主状态 |
| `.nextflow/history` | 本机执行/会话查找材料 | 私有引擎恢复/诊断数据 |
| `work/<task>/.command.sh`, `.command.run`, `.command.begin`, `.exitcode` | 生成的任务脚本、包装器和任务本地进度/退出材料 | 内部证据；任务退出文件不能证明整个工作空间的终止 |
| `work/<task>/.command.out`, `.command.err`, `.command.log` | 本机任务诊断 | 私有临时文件或明确保留的诊断数据 |
| 任务目录之间的阶段输入符号链接 | 本机输入绑定，不涉及新输出所有权 | 无跟随的库存；声明的链接交付品被拒绝 |
| `results/*.result.txt` | 明确发布的候选 | 只有在宿主批准后，才验证/复制到已有的不可变构件版本中 |
| `trace-*.tsv`, `.nextflow.log`, 引擎创建的元数据目录 | 诊断观察，包括路径和时间 | 保留原始文件；仅发布选定的可移植事实 |
| `engine-home/` 和 `tmp/` | 运行时本地目录，包括该固定环境中的空本机秘密目录 | 私有临时文件，不是包内容或继承的提供者凭证 |
| `JOB/attempts/` 和 `JOB/artifacts/` | 宿主计划、意图、确认和接受的修订 | 位于工作负载的可写和可回收树之外 |

并发库存读取是诊断性的，不是原子快照。它们标记已更改/消失的条目。宿主在自身终止门之后，仅在获得新鲜限定库存后，才进行接受/回收决策。文件系统事件和引擎退出标记不足以作为权威。

[Nextflow的缓存契约](https://docs.seqera.io/nextflow/cache-and-resume) 要求在恢复时同时保留缓存元数据和本机工作文件。观察确认，仅保留导出结果会丢失有用的引擎恢复材料。这不是保留每个内部文件永久的理由：保留恢复材料直到明确放弃，然后一起收集。

## 调整失败和修复

两个准备失败被保留而不是静默重试：

- 下载的分发最初不是可执行文件。其启动器错误地解析了绝对脚本调用并尝试下载。沙箱拒绝了它。在依赖准备期间，应使已验证的分发在运行时可执行；不要在工作负载期间授予网络访问权限。
- 限定的Homebrew JVM在初始政策下甚至对于`java -version`也崩溃。其崩溃堆栈结束于系统属性初始化。孤立的政策探针显示，仅允许macOS用户目录服务查找`com.apple.system.opendirectoryd.libinfo`可修复启动。既没有通用的Mach允许规则，也没有更广泛的文件系统/网络访问。相同的狭窄服务允许在已审查的本地Codex沙箱实现中存在。

宿主在scratch库存失败时也保留进程记录，而不是在库存错误后丢失终止证据。链接输出回归测试该记录路径；无效库存仍直到精确允许的文件树可以验证才拒绝收集。

## 最小可复用宿主边界

伴机宿主变更添加了操作员拥有的 `workspace-run`，`workspace-resume`，`workspace-accept` 和 `workspace-reclaim` 操作。它使用了现有的监督者、不可变修订发布者和消费者 API。它不添加另一个 artifact 数据库、事件调度器、工作流语言或 VM 控制器。一个原生测试将新的修订输入到现有的 kernel-admitted 文件 kit，既在收集前也将在收集后喂入，检查固定输入和应用执行证据。

延续绑定一个显式的前驱和当前 scratch 存储库存。缺失或不确定的凭证、活跃锁和过时的前驱拒绝延续或收集。接受检查选择的输入和精确候选字节，拒绝失败/取消和链接输出，并限制重复/不完整发布。收集是单独批准的，并声明恢复将丢失。一个输出变更或延迟文件将无效对应审核计划。

现有的 file-kit ABI 和其更严格的流程限制保持不变。
工作流特定的任务顺序、缓存含义、结果验证和未来代理指令仍保留在示例/spool 中。工具原生的磁带保持其所有者；没有标准化的模型转录或提供者计费系统被引入。

## 限制和下一步工作

新的配置是针对**经过审核的本地工具，不进行守护进程**的。它拥有一个进程组，回收其领导者，并检查组空闲性；它不能认证逃逸的工作者、远程作业或对抗性过程树行为。源/配置批准不是替代更强大的后端，用于不受信任的编码代理。这里没有通用的 JVM 负载、Linux 工作区后端、状态迁移、远程恢复、周期性保留或正式-制品 GC 的资格。

在这一首个配置中，scratch 保留是手动和显式的。一个有限的恢复租约/调度器是未来工作，不是已实现的保证。正式输出是受限的 UTF-8 文件；多输出发布不是原子事务，且没有独立的备份或电源失效恢复被声称。原生运行时路径必须保持可用；保留的文件不使外部依赖可恢复。

下一步有用的验证是使用此边界的一个真实域工作流，其自身有输出检查。一个活体编码工具适配器必须单独证明权威性、取消和凭证行为。两者都不需要替换 Nextflow 的缓存或使 Loom 成为运行时权威。
