# Weaver: reviewed domain knowledge to spool development

Weaver is an optional task-preparation and candidate-review role. A plugin may
reuse an existing harness; Loom does not implement its model loop. Domain source
selection, rules and tests belong to the project, not the framework.

The first example uses public log materials: select exact sources, draft a
DOMAIN.md with source references and unresolved questions, review its exact bytes
and the protected acceptance script, then submit a bounded kit assignment to a
mature coding CLI. A source, specification or acceptance change invalidates the
review. Candidate code cannot redefine those files. Review means agreement on
requirements, not permission to execute or disclose unrelated private sources.

Keep selected source digests, draft/review identities, candidate identity and
check results. Hashes bind bytes; they do not authenticate a reviewer or prove
that domain rules are true. Local authority files must remain operator-owned.
An external coding tool retains its own context and tape. A private source is not
published merely because a derived rule is included in a package.

## Independent and managed operation

A spool may provide a standalone CLI for development without installing or
mounting an-agent. This zero-mount mode supports local domain tests and ordinary
Loom check/pack/verify. It runs with the operator's native authority; it does not
supply host isolation, settlement, grants or formal artifact custody. Independent
results must not be fabricated into receive-check/pack-task host evidence.

Formal operation managed by our platform requires an-agent admission, selected
release/instance identity, an explicit execution grant and host settlement and
artifact acceptance. Loading alone is not activation or execution approval.
Independent iteration does not change these requirements. This is a platform
contract, not a claim that a public executable cannot be launched elsewhere.

## Ownership

- Weaver: propose sourced requirements and tests; surface conflicts; review code
  against the approved rules. It cannot approve its own authority.
- Loom: version development material, protect baselines, receive candidates,
  organize checks and package exact selected bytes. Offline packaging remains
  available, and has no controlled-execution claim.
- an-agent: authorize access/disclosure and execution, supervise attempts and own
  accepted state/products. It does not interpret domain rules.
- Developer: resolve domain ambiguity, confirm the specification, and decide
  release/permission changes. Coding tools implement the scoped assignment.

A vendor hook is an optional entrypoint, not a mandatory global prompt interceptor
or a security boundary. Model output and retrieved documents remain untrusted
inputs. Prefer explicit source selection and a reviewed task over opaque prompt
rewriting. Existing bounded context APIs do not provide a universal knowledge-base
permission service. The host kit-proposal slot is not Weaver.

The first implementation is an example adapter with file contracts, not a general
Weaver runtime or multi-file coding-agent sandbox. A different harness can replace
the adapter while preserving reviewed inputs and candidate outputs.
